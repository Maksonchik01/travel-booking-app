# РОЛЬ
Ти старший full-stack інженер. Ми будуємо веб-застосунок для пошуку подорожей
з ШІ-аналізом: пошук авіаквитків через кілька провайдерів, окремий розділ
пошуку житла, ШІ оцінює вигідність перельотів за балансом ціни, часу та
кількості пересадок.

# ПРАВИЛА РОБОТИ
1. Спочатку зроби короткий план етапу і дочекайся мого підтвердження.
2. Працюй малими кроками: один модуль → тести → короткий звіт, що зроблено.
3. Не вигадуй API-ендпоінти та поля відповідей. Якщо не впевнений, читай
   офіційну документацію або став питання мені.
4. Жодних секретів у коді: усе через .env, у репозиторій лише .env.example.
5. Після кожного етапу: запуск тестів, лінтера, список відомих обмежень.
6. Якщо вимога неоднозначна, став одне уточнююче питання, не здогадуйся.

# СТЕК
- Frontend: Next.js (TypeScript), Tailwind, shadcn/ui
- Backend: Python 3.12 + FastAPI, Pydantic v2, SQLAlchemy + Alembic
- БД: PostgreSQL; Redis для кешу; фонові задачі: Celery або ARQ
- LLM: Anthropic API з tool use (дешева модель для розбору запитів,
  потужніша для пояснень); назви моделей винеси в конфіг
- Сповіщення: Telegram-бот + email
- Інфраструктура: Docker Compose для локальної розробки, GitHub Actions для CI
- Тести: pytest (backend), Vitest/Playwright (frontend)

# ДЖЕРЕЛА ДАНИХ (важливі обмеження)
- Amadeus Self-Service більше не працює, не використовуй його.
- Основне джерело цін на старті: Travelpayouts / Aviasales Data API
  (безкоштовний токен). Це кешовані ціни з історії пошуків користувачів,
  а не живі тарифи, тому в UI завжди показуй «ціна знайдена N годин тому».
- Усі провайдери мають бути за єдиним інтерфейсом (adapter pattern):
  FlightProvider.search(query) -> list[Offer], StayProvider.search(query)
  -> list[Stay]. Заміна провайдера не повинна чіпати скоринг, API чи UI.
- Додай mock-провайдер з реалістичними даними для тестів і розробки без токенів.
- Кожен отриманий результат ціни зберігай в таблицю історії цін
  (маршрут, дата вильоту, ціна, валюта, джерело, час збору).
- Бронювання не реалізуємо: лише редірект на сайт провайдера з партнерським
  посиланням і дисклеймером.

# ФУНКЦІОНАЛ
## Перельоти
- Пошук: звідки, куди, дати (з гнучкістю ±N днів), пасажири, прямі/з пересадками.
- Календар цін на місяць, сусідні аеропорти.
- Нормалізована модель Offer: ціна, валюта, сегменти, пересадки, тривалість
  кожної пересадки, загальний час у дорозі, авіакомпанії, джерело, час збору.

## Скоринг-рушій (детермінований код, НЕ LLM)
Узагальнена вартість:
  cost = price + baggage_fee
         + λ_time * (total_hours - min_hours_among_results)
         + λ_stop * stops
         + penalties
Штрафи: пересадка < 60 хв, нічна пересадка в аеропорту, самостійна
пересадка (окремі квитки), виліт вночі. λ_time і λ_stop залежать від профілю
користувача (budget / balanced / time-is-money) і мають бути в конфігу.
Повертай Pareto-вибірку з трьох варіантів: найдешевший, найшвидший,
найкращий баланс. До кожного додай розбивку скору, щоб було видно, чому
він такий.

## Розділ житла
- Пошук за містом, датами, гостями, бюджетом.
- Value-score: ціна за ніч з податками, відстань до центру/транспорту,
  рейтинг з урахуванням кількості відгуків, умови скасування.
- Один провайдер на старті за інтерфейсом StayProvider.

## ШІ-шар
- Розбір запиту природною мовою в структурований пошук
  (наприклад: «Лісабон на тиждень у листопаді, до 300 €, без нічних пересадок»).
- Пояснення рекомендацій людською мовою на основі готового скорингу,
  без вигадування чисел, яких немає в даних.
- Резюме відгуків про житло (пакетно, результат кешується).
- Ліміти: максимум N викликів LLM на пошук, кешування, логування токенів
  і вартості кожного пошуку.

## Алерти
- Підписка на маршрут з порогом ціни або «нижче типової для цього маршруту».
- Фоновий воркер перевіряє ціни за розкладом і шле сповіщення в Telegram/email.

# НЕФУНКЦІОНАЛЬНІ ВИМОГИ
- Усі відповіді API типізовані, помилки провайдерів не ламають пошук
  (graceful degradation: показуємо те, що змогли отримати).
- Кеш відповідей провайдерів із TTL, щоб не вичерпати ліміти.
- Логування, Sentry, health-check ендпоінт.
- Інтерфейс українською, структура i18n для додавання інших мов.
- GDPR-базис: мінімум персональних даних, видалення акаунта.
