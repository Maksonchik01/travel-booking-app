# ADR 0032 — Синхронізація між модулями

Статус: прийнято (модуль 15).

## Контекст

ТЗ модуля 15 описує вісім переходів між модулями. Дані між ними мають передаватися без дублювання бізнес-логіки в компонентах. Аудит показав, що більшість переходів уже є:

| Перехід | Як працює | Де |
|---|---|---|
| житло → поїздка | `stay=` у `/trip` (модуль 7) | `lib/trip-params.ts` `tripFromStay` |
| ШІ → поїздка | «Відкрити в планувальнику» з карток чату (9b) | `chat-cards.tsx` |
| поїздка → ШІ | «Оптимізувати з ШІ», подія `ai:open` (9b) | `lib/ai-events.ts` |
| пошук → обране | `FavoriteToggle` на картках (8c, 10a) | `lib/favorites.ts` |
| обране → пошук | «Повторити пошук» / «Відкрити в планувальнику» | `favorites.tsx` |

Бракувало трьох речей:
- переходу «рейс → поїздка»;
- переходу «збережена поїздка → сповіщення»;
- налаштувань кабінету у формі поїздки й у ШІ-помічнику.

## Рішення

1. **Єдиний стан — URL.** Кожен перехід — посилання на сторінку іншого модуля з тими самими параметрами URL, а не копія даних. Посилання будуються в одному місці, `lib/trip-params.ts`:
   - `tripFromStay` (перенесено з `stay-card.tsx`);
   - новий `tripFromFlight`, через спільний `toTripParams`.

   Суми, скоринг і вибір рахує API. Компоненти лише показують результат.
2. **Рейс → поїздка.** На картці рейсу є кнопка «Додати до поїздки». Вона відкриває `/trip` з тим самим маршрутом і умовами (люди, клас, багаж, «лише прямі», сусідні аеропорти). Дати — фактичні дати рейсу, тож це працює і для гнучкого пошуку. Рейс закріплено через `flight=` (8b). Планувальник шукає житло на дати цього рейсу, а якщо рейс більше не знаходиться, чесно про це пише. Кнопки немає для рейсів в один бік і для пошуків з немовлятами: поїздка рахує лише дорослих і дітей.
3. **Поїздка → сповіщення.** Збережена поїздка має посилання «Стежити за ціною». Воно веде на `/trip?…#price-alert`, до того самого блоку `PriceAlert`, що й на сторінці результатів. Окремої логіки підписки немає. Сповіщення для поїздки працюють лише з реальним джерелом житла (ADR 0026), інакше блок пояснює, чому вони недоступні.
4. **Кабінет → усі модулі.** Нові пошуки беруть значення з профілю:
   - **Форма поїздки** (`tripDefaults`): домашній аеропорт, клас, багаж, «лише прямі», пріоритет, умови житла. Перенесене з іншого режиму важить більше (`withTripDraft`).
   - **Пошуки поїздки, житла й перельотів:** м'які уподобання з профілю (ADR 0031).
   - **ШІ-помічник.** Веб-маршрут `/api/ai/chat` на сервері підставляє з акаунта домашній аеропорт, валюту (якщо відкритий пошук не має своєї) й уподобання. Валюта й аеропорт ідуть у контекст моделі. Уподобання застосовує лише код скорингу, моделі їх не передаємо: мінімум даних.
   - Відкритий з URL пошук профіль не змінює і профілем не перезаписується.

## Наслідки

- Нова сторінка-ціль для переходу — новий хелпер у `lib/trip-params.ts`, а не логіка в компоненті.
- Сторінка конфіденційності описує, що з профілю бачить помічник.
