# ADR 0034 — Кеш, стійкість запитів до джерел і свіжість цін

Статус: прийнято (модуль 17a: 17.1–17.4).

## Контекст

SerpApi — живі ціни з квотою 250 запитів на місяць. Travelpayouts — кешований API без квоти на запит, але з лімітом частоти. До модуля 17:
- кеш Redis уже був (`CachedFlightProvider`, TTL 30 хв);
- повторів, ліміту одночасних запитів і об'єднання однакових запитів не було: десять людей, які одночасно шукають той самий маршрут, давали десять викликів SerpApi;
- ціна мала лише два стани, `live` і `cached`.

## Рішення

1. **Ключ кешу (17.1)** — `search_cache_payload`: усе, що змінює відповідь джерела. Це маршрут, дати й гнучкість, пасажири, клас, валюта, сусідні аеропорти й «лише прямі». Профіль, фільтри, багаж і уподобання до джерела не йдуть, тож у ключ не входять: багаж SerpApi ціну не змінює (ADR 0014). У ключ продавців додано склад і клас. Обидва набори полів закріплено тестами.
2. **Шлюз запитів (17.2)** — `providers/gate.py` `ProviderGate`, по одному на джерело (спільний пул екземплярів у `main.py`):
   - семафор одночасних запитів: SerpApi — 4, Travelpayouts — 6;
   - повтор лише транзитних збоїв: обрив з'єднання, 502/503/504. Затримка 2ⁿ з розкидом 50–100 % і стелею, пауза поза семафором;
   - 429 і 4xx не повторюються: квоту чи помилку запиту повтор не виправить;
   - SerpApi: 2 спроби, тайм-аут не повторюється (невідомо, чи запит списав квоту, і повтор не вкладеться в ліміт часу). Travelpayouts: 3 спроби, тайм-аут повторюється.

   Загальний тайм-аут джерела в `FlightSearchService` лишається над шлюзом.
3. **Однакові запити — один виклик (17.2).**
   - **У процесі:** спільна задача (`_shared`). Скасування одного очікувача, наприклад через тайм-аут його пошуку, не скасовує виклик для інших.
   - **Між процесами:** замок у Redis (`SET NX EX 60`). Хто взяв замок, іде до джерела. Інші до 25 с чекають, поки відповідь з'явиться в кеші. Якщо власник замка впав чи отримав помилку, вони йдуть до джерела самі.
   - Без Redis пошук працює як раніше.
4. **Обмеження частоти (17.2):** на вході — `core/rate_limit.py` (на відвідувача). На виході — семафор шлюзу, бюджет запитів SerpApi на пошук і `ALERT_MAX_SEARCHES_PER_RUN` для перевірок сповіщень. Помилки джерел мають статус у відповіді (`ProviderStatus`), пошук не падає.
5. **Свіжість (17.3)** — `domain/freshness.py`, `FlightSearchResult.freshness` і `StaySearchResult.freshness`. Час отримання кожної ціни вже зберігався (`collected_at`, `found_at` / `found_on`). Стани:
   - `live` — живе джерело, до `PRICE_LIVE_FRESH_MIN` (30 хв, як TTL кешу);
   - `cached` — кешоване джерело з відомим віком, до `PRICE_CACHED_STALE_DAYS` (3 дні);
   - `approximate` — кешоване, коли знайдено невідомо;
   - `needs_recheck` — давніше. UI показує значок біля віку ціни; перевірити ціну можна у продавців або через «Оновити ціни».
6. **Секрети й PII (17.4):**
   - ключі джерел є лише в API (`Settings`, `SecretStr`). Веб звертається до API зі свого сервера. У браузер потрапляють тільки змінні `NEXT_PUBLIC_*`. Тест `server-boundary.test.ts` перевіряє, що жоден клієнтський компонент не імпортує серверних модулів і не читає непублічних змінних;
   - логи: httpx/httpcore не нижче WARNING (URL з ключем SerpApi), Sentry без PII і з чищенням breadcrumbs. Новий процесор `redact_secrets` маскує ключі `api_key`, `token`, `password`, `email`… та `api_key=…` чи email у тексті будь-якого запису. Це другий рубіж, якщо хтось залогує зайве.

## Наслідки

- Новий HTTP-адаптер джерела ходить через `ProviderGate`, а не напряму через `httpx`.
- Нове поле запиту, що змінює відповідь джерела, автоматично потрапляє в ключ кешу. Поле лише для видачі треба додати в `CACHE_EXCLUDED` разом із тестом.
- Сторінка «Як це працює» описує позначки свіжості.
