# ADR 0008: Розділ житла, value-score і помічник у трьох режимах

- Статус: прийнято (2026-11-06)

## Контекст
ТЗ: пошук житла за містом, датами, гостями й бюджетом; value-score з ціни за ніч з
податками, відстані до центру й транспорту, рейтингу з урахуванням кількості відгуків і
умов скасування; один провайдер за `StayProvider`; резюме відгуків від ШІ.

Готельного API, доступного без схвалення, немає: Hotellook (Travelpayouts) закрито в
жовтні 2025, Booking.com / Expedia — лише після партнерської заявки. SerpApi Google Hotels
працює, але ділить квоту з перельотами (250 запитів/міс), а відгуки — ще запит на кожен
об'єкт. Власник вирішив: **поки лише mock** (`STAY_PROVIDERS=mock`).

## Рішення
- **Модель і інтерфейс:** `domain/stays.py` (`StayQuery`, `Stay`, `StayReview`),
  `StayProvider.search(query) -> list[Stay]` і `.reviews(stay_id)`. Ціни — з податками,
  за весь номер; рейтинг — шкала 0–10; невідоме — `None` («невідомо», а не «ні»).
  Місто — код міста або аеропорту (WAW → Варшава, `AirportDirectory.city_of`); центр —
  координати міста з довідника.
- **Mock** (`providers/mock_stays.py`): детермінований; об'єкт сталий для міста (де
  стоїть, рейтинг, відгуки), ціна залежить від дат і гостей. Є всі випадки для скорингу
  й аналізу: мало відгуків, далеко від центру, невідомі умови, повторювані скарги,
  prompt injection у відгуку.
- **Value-score** (`scoring/stays.py`, ваги — `scoring/stays.toml`): за ніч у валюті
  пошуку, менше — вигідніше (як для перельотів):
  `ціна + λ_distance·max(0, км − 1) + штраф за транспорт > 800 м
   + λ_rating·max(0, 9 − скоригований рейтинг) + штраф за умови скасування`.
  Скоригований рейтинг — байєсівське середнє `(n·r + 20·7,5) / (n + 20)`: 9,8 з 4
  відгуків не перемагає 9,1 з 1200. Невідомі відстань, транспорт чи умови — лише
  попередження. Профілі: ціна / баланс / центр. Вибір: найдешевший, збалансований
  (найменша оцінка), найкращий рейтинг.
- **Сервіс** (`services/stay_search.py`): провайдери паралельно з таймаутом, збій одного
  не ламає відповідь; фільтри (бюджет на ніч, рейтинг, безкоштовне скасування, тип) —
  після провайдерів; кожна ціна — в `stay_price_history` (місто з запиту).
- **Резюме відгуків** (`ai/stay_analyst.py`, роль власника `sub-agents/Stay-Analyst.md`):
  лише на вимогу, для «Нашого вибору» (до 3 об'єктів), кешується. Код перевіряє: id лише
  з входу, `top_pick_id` = вибір value-score, числа — з входу або лічильники відгуків
  («6 з 30»); < 10 відгуків — надійність «low» незалежно від моделі.
- **Помічник — три окремі чати** (`ai/assistant.py`, `mode`): «Квитки», «Житло», «Уся
  поїздка». Кожен має свій промпт (`ai/prompts/*-Assistant.md`) і свої інструменти: у чаті
  житла модель не бачить пошуку квитків і навпаки. Перше питання («Що шукаємо?») — готовий
  текст UI, без виклику моделі. Історія кожного режиму — окремо в sessionStorage вкладки.
  «Уся поїздка»: переліт, потім житло з дня прильоту до повернення; суму не рахує — це
  етап 6 (комбінований підбір).

## Наслідки
- Ціни й відгуки житла — вигадані mock-дані; UI позначає джерело «Тестові дані».
  Реальне джерело — ще один адаптер `StayProvider` + кеш Redis, решта не змінюється.
- Резюме відгуків — запит до потужнішої моделі (`LLM_MODEL_EXPLAINER`) на вимогу; з
  реальним джерелом відгуки ще й витрачатимуть квоту, тому автоматично не запускаються.
